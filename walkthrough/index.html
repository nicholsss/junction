Where this sits in a pull-request flow

The receipt replaces “read the whole diff” with “check the evidence, then decide”. This is what is built today.

  1. 1
    Agent opens a pull request

    A change arrives with a requirement ID.

    Built Four demo PRs, each based on the AI commit’s parent.
  2. 2
    Harness runs the checks

    Only the harness writes check results.

    Partly built Results recorded from scripts in evidence/. No runner yet.
  3. 3
    Model proposes, engine decides

    DeepSeek proposes claims; the engine computes each status.

    Built Built, run on R2283.
  4. 4
    Rules route attention

    Named rules set the depth and the places to read.

    Built Built.
  5. 5
    A named human decides

    Accept listed risks, request changes, or escalate, bound to the head SHA.

    Built CLI reads the human’s PR comment and sets a status for that head. Run manually; no event automation.

+### Generic types from referenced assemblies
+
+Closed generic types defined in a referenced assembly (for example, `Item<int>` where `Item<T>` is defined in another project or NuGet package) can be used as members of your `[MessagePackObject]` types, including generic value types and record structs.
+Diagnostics about the members of such a type are reported by the assembly that defines it rather than by the consuming project, so any problem must be fixed there.
+
 ### MagicOnion
 
 [MagicOnion](https://github.com/Cysharp/MagicOnion) is a code-first gRPC framework based on grpc-dotnet and MessagePack. gRPC usually communicates with Protocol Buffers using IDL. But MagicOnion uses MessagePack for C# and does not need IDL. When communicating C# to C#, schemaless (or rather C# classes as schema) is better than using IDL.

Principles, trade-offs and limits

Our recommendation: automate repeatable checks and focus human judgment on consequential uncertainty.

Risk: escalate scope changes and missing evidence. Hallucination: check citations and executed tests; semantic mistakes remain possible. Transparency: show source, provenance and gaps. Confidence: scope each statement rather than give a score. Quality: track misses and outcomes alongside time saved.

Seven principles

  1. Three kinds of statement, never mixed. Executed checks (written only by the harness), AI claims (status computed), and AI refusals (questions for the human).
  2. A model’s prose cannot become evidence. The model never sets a status. The engine re-resolves each citation and computes it.
  3. A claim is verified only through a named test that ran. A whole-suite pass cannot verify a specific claim; that link goes to a human.
  4. Failed, skipped and not-run checks stay visible. None becomes a pass.
  5. Route attention by named rules. No trust score. Each review depth lists the rules that fired and what was observed.
  6. Decisions are bound to a commit. A different head SHA makes the receipt stale.
  7. Ownership stays human. No automatic approval or merge.

Trade-offs

  • Fewer verified claims, more human attention. That is deliberate.
  • Rules over a score: rules can be argued with and tuned. The cost is that thresholds are guesses until measured.
  • Deterministic engine, advisory model: the model adds coverage but its claims are only as good as its choice of claim.
  • Probes versus gates: a mislabelled probe could hide a real failure.

Limits

  • Relevance is not proven: the engine checks that a named test exists and ran, not that it tests what the claim says.
  • A citation proves the lines exist, not that they say what the claim says, so code claims reach “source only” at most.
  • One repository, one machine, .NET 8. The two-project repro from the issue was not run.
  • The crash-only comparison is a local hand-applied approximation of a reference fix; it is not a run of that reference patch.
  • GitHub integration runs manually. A pull_request Action and branch protection requiring review-receipt are not built. The page is a snapshot; new pushes have no successful review-receipt status, and the CLI detects stale evidence when run.
  • Bot and human share one login in a single-account demo; prefer a teammate’s own account. No signer has been assigned.
  • The 400-line threshold is untuned. Nothing here shows long-term reliability.
